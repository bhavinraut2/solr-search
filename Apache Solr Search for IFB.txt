In an AEM Sites (Cloud Service) + Adobe Commerce (PaaS) + Apache Solr architecture like IFB Appliances, wrong search results typically come from poor indexing strategy, weak schema design, improper analyzers, or missing contextual signals (category, intent, synonyms, canonicalization).
Below is a structured best-practice guide tailored to a multi-category brand like IFB Appliances.
________________


1️⃣ First: Define the Search Architecture Clearly
Before tuning Solr, confirm:
* Is Solr indexing from Adobe Commerce only, or from both AEM + Commerce?
* Is AEM querying Solr directly, or via a middleware layer?
* Are CMS pages (blogs, service pages, support) indexed in the same core as products?
Best Practice
👉 Use separate cores/collections:
* products_core
* cms_core
* support_core
Then implement federated search logic at AEM layer.
Why?
Mixing dishwashers with blog articles in one ranking model causes relevance confusion.
________________


2️⃣ Schema Design Best Practices (Most Critical)
For a brand like IFB (washing machines, ACs, modular kitchens, additives etc.), schema design determines contextual relevance.
A. Use Explicit Field Strategy (Not Catch-All)
Avoid indexing everything into one text field.
Instead define:
product_name (text_en)
sku (string)
category (string)
sub_category (string)
brand (string)
series (string)
capacity (float)
color (string)
price (float)
description (text_en)
features (text_en)
intent_tags (string multivalued)
url (string)
canonical_url (string)
is_product (boolean)

________________
B. Boost Critical Fields
In solrconfig.xml:
qf=product_name^8 category^5 features^3 description^2
Example:
If user searches "8kg washing machine"
* capacity should match numerically
* category = washing machine boosted
* product_name highest boost
Without boosting, Solr ranks random text matches.
________________


C. Use Multi-Valued Fields for Facets
For IFB:
energy_rating
installation_type
capacity_range
inverter_type
Faceting should not affect ranking, but improves UX filtering.
________________


3️⃣ Analyzer & Tokenization Configuration
IFB products contain:
* Numbers (8kg, 1.5 ton)
* Hyphenated models (IFB-Diva-SX)
* Acronyms (AC, MWO)
Use:
For text fields:
StandardTokenizer
LowerCaseFilter
StopFilter
SynonymFilter
WordDelimiterGraphFilter
Critical: WordDelimiterGraphFilter
It allows:
* "1.5ton" → "1", "5", "ton"
* "8kg" → "8", "kg"
* "IFB-Diva-SX" → IFB, Diva, SX
Without this, model search fails.
________________


4️⃣ Synonym Strategy (Extremely Important for Appliances)
Create domain synonym file:
wm => washing machine
ac => air conditioner
mwo => microwave oven
dw => dishwasher
front load => fl
top load => tl
For India-specific usage:
washing powder => detergent
Synonyms must be:
* Index-time OR query-time
* Query-time preferred (easier updates)
________________


5️⃣ Contextual Search (Intent-Based)
Problem:
User searches “leakage issue” and sees washing machine products.
Solution: Intent Tagging
Add metadata:
intent_tags:
  - buy
  - repair
  - installation
  - accessories
Then:
* If search term contains “service”, boost support core
* If “price”, boost product core
* If “manual”, boost support core
This logic should be implemented in AEM before querying Solr.
________________


6️⃣ Category-Aware Search (Huge Impact)
IFB has unrelated categories:
* Modular kitchen
* Washing machine
* AC
When user navigates inside AC category, search should be contextual.
Best Practice:
Pass fq=category:AC filter when user is inside AC PLP.
This prevents dishwasher results when searching "1.5 ton".
________________


7️⃣ Canonical URL Strategy
Solr should index only canonical product URLs.
Example:
Bad:
/product?id=123
/washing-machines/front-load?id=123
Good:
/washing-machines/front-load/ifb-diva-sx-8kg
Implementation Best Practice
* Adobe Commerce should define canonical product URL
* AEM must fetch and store canonical_url field
* Solr indexes only canonical_url
* Use canonical URL as uniqueKey
In schema.xml:
<uniqueKey>canonical_url</uniqueKey>
This prevents duplicate result ranking issues.
________________


8️⃣ Commerce → Solr Data Sync Best Practices
Never index incomplete product data.
Ensure:
* All attributes normalized
* Category hierarchy flattened
* Clean HTML stripped from description
* Units standardized (kg, ton, L)
Bad Data = Bad Search.
________________


9️⃣ Boosting Based on Business Signals
For IFB:
Boost:
* In-stock products
* New launches
* Best sellers
Example:
bf=recip(ms(NOW,publish_date),3.16e-11,1,1)^2
Or simple:
in_stock:true^5

________________
🔟 Handling Numeric & Range Queries Properly
User searches:
* “8kg washing machine”
* “1.5 ton inverter ac under 40000”
You must:
* Map numeric tokens to numeric fields
* Parse price filters
* Use Solr Range Query
Example:
capacity:[7 TO 9]
price:[* TO 40000]
This requires AEM-side query preprocessing.
________________


1️⃣1️⃣ Use Learning-to-Rank (If Enterprise-Scale)
For large catalog:
* Implement Solr LTR
* Train model using click-through data
* Re-rank top 50 results
This significantly improves contextual accuracy.
________________


1️⃣2️⃣ Debugging Wrong Results Checklist
If search returns wrong products:
✔ Check analyzer output
✔ Check field boosts
✔ Verify category filter
✔ Check if description has noisy HTML
✔ Confirm synonyms
✔ Validate numeric parsing
✔ Inspect query debug (debugQuery=true)
________________


1️⃣3️⃣ AEM Layer Responsibilities
AEM should:
* Detect user persona
* Pass category filter
* Add boost parameters
* Query multiple cores if needed
* Merge results intelligently
Solr alone cannot solve intent.
________________


1️⃣4️⃣ Ideal Final Architecture for IFB
Adobe Commerce → Product Feed → Solr (products_core)
AEM CMS → Solr (cms_core)
AEM UI → Intent Processor → Solr Query Builder
Solr → Ranked Results → AEM → UI

________________
🚨 Most Common Mistakes in This Setup
* Single generic text field
* No field boosting
* No synonyms
* No category filtering
* Duplicate URLs indexed
* Mixing CMS & product ranking logic
* Not normalizing units
________________


🎯 If You Want Immediate Improvement
1. Add field boosts
2. Add synonym file
3. Enable WordDelimiterGraphFilter
4. Filter by category context
5. Use canonical_url as uniqueKey
6. Separate product & CMS cores
________________

A sample Solr schema.xml optimized for appliance ecommerce


Below is a sample Apache Solr schema.xml optimized for an appliance e-commerce setup like IFB Appliances (washing machines, ACs, microwave ovens, dishwashers, modular kitchen, additives, etc.).
This schema is designed for:
* Strong product-name relevance
* Proper numeric handling (8kg, 1.5 ton, price filters)
* Category-aware search
* Faceting support
* Synonym-ready configuration
* Canonical URL-based uniqueness
* Commerce + AEM compatible architecture
________________


✅ Design Principles Used
* Explicit field modeling (no catch-all only indexing)
* Boost-friendly text fields
* Numeric fields for range queries
* Facet-optimized string fields
* Query-time synonyms
* Word delimiter for model numbers
* Canonical URL as uniqueKey
________________


📄 Sample schema.xml
<?xml version="1.0" encoding="UTF-8" ?>
<schema name="appliance-ecommerce" version="1.6">


  <!-- ========================= -->
  <!-- Unique Identifier -->
  <!-- ========================= -->
  <uniqueKey>canonical_url</uniqueKey>


  <!-- ========================= -->
  <!-- Field Types -->
  <!-- ========================= -->


  <!-- Text with search analysis -->
  <fieldType name="text_en" class="solr.TextField" positionIncrementGap="100">
    <analyzer type="index">
      <tokenizer class="solr.StandardTokenizerFactory"/>
      <filter class="solr.LowerCaseFilterFactory"/>
      <filter class="solr.StopFilterFactory" ignoreCase="true" words="stopwords.txt"/>
      <filter class="solr.WordDelimiterGraphFilterFactory"
              generateWordParts="1"
              generateNumberParts="1"
              splitOnCaseChange="1"
              preserveOriginal="1"/>
      <filter class="solr.SynonymGraphFilterFactory"
              synonyms="synonyms.txt"
              expand="true"
              ignoreCase="true"/>
    </analyzer>


    <analyzer type="query">
      <tokenizer class="solr.StandardTokenizerFactory"/>
      <filter class="solr.LowerCaseFilterFactory"/>
      <filter class="solr.SynonymGraphFilterFactory"
              synonyms="synonyms.txt"
              expand="true"
              ignoreCase="true"/>
      <filter class="solr.WordDelimiterGraphFilterFactory"
              generateWordParts="1"
              generateNumberParts="1"
              preserveOriginal="1"/>
    </analyzer>
  </fieldType>


  <!-- Exact string (facets, filters, sorting) -->
  <fieldType name="string" class="solr.StrField" sortMissingLast="true"/>


  <!-- Boolean -->
  <fieldType name="boolean" class="solr.BoolField"/>


  <!-- Numeric fields -->
  <fieldType name="pfloat" class="solr.FloatPointField"/>
  <fieldType name="pdouble" class="solr.DoublePointField"/>
  <fieldType name="pint" class="solr.IntPointField"/>
  <fieldType name="plong" class="solr.LongPointField"/>


  <!-- Date -->
  <fieldType name="pdate" class="solr.DatePointField"/>


  <!-- ========================= -->
  <!-- Product Core Fields -->
  <!-- ========================= -->


  <!-- Identity -->
  <field name="sku" type="string" indexed="true" stored="true"/>
  <field name="product_id" type="string" indexed="true" stored="true"/>
  <field name="canonical_url" type="string" indexed="true" stored="true"/>


  <!-- Core Search Fields -->
  <field name="product_name" type="text_en" indexed="true" stored="true"/>
  <field name="short_description" type="text_en" indexed="true" stored="true"/>
  <field name="long_description" type="text_en" indexed="true" stored="false"/>
  <field name="features" type="text_en" indexed="true" stored="false"/>


  <!-- Catch-all searchable field -->
  <field name="text" type="text_en" indexed="true" stored="false" multiValued="true"/>


  <!-- Category Structure -->
  <field name="category" type="string" indexed="true" stored="true" multiValued="true"/>
  <field name="sub_category" type="string" indexed="true" stored="true" multiValued="true"/>
  <field name="category_path" type="string" indexed="true" stored="true"/>


  <!-- Brand & Series -->
  <field name="brand" type="string" indexed="true" stored="true"/>
  <field name="series" type="string" indexed="true" stored="true"/>


  <!-- Appliance-Specific Attributes -->
  <field name="capacity_kg" type="pfloat" indexed="true" stored="true"/>
  <field name="capacity_litre" type="pfloat" indexed="true" stored="true"/>
  <field name="cooling_ton" type="pfloat" indexed="true" stored="true"/>
  <field name="power_watt" type="pint" indexed="true" stored="true"/>
  <field name="energy_rating" type="string" indexed="true" stored="true"/>
  <field name="color" type="string" indexed="true" stored="true" multiValued="true"/>
  <field name="installation_type" type="string" indexed="true" stored="true"/>


  <!-- Pricing -->
  <field name="price" type="pdouble" indexed="true" stored="true"/>
  <field name="mrp" type="pdouble" indexed="true" stored="true"/>
  <field name="discount_percent" type="pfloat" indexed="true" stored="true"/>


  <!-- Inventory -->
  <field name="in_stock" type="boolean" indexed="true" stored="true"/>
  <field name="stock_qty" type="pint" indexed="true" stored="false"/>


  <!-- Business Signals -->
  <field name="is_new_launch" type="boolean" indexed="true" stored="true"/>
  <field name="is_best_seller" type="boolean" indexed="true" stored="true"/>
  <field name="rating" type="pfloat" indexed="true" stored="true"/>
  <field name="review_count" type="pint" indexed="true" stored="true"/>


  <!-- Intent Tagging -->
  <field name="intent_tags" type="string" indexed="true" stored="true" multiValued="true"/>


  <!-- SEO -->
  <field name="meta_title" type="text_en" indexed="true" stored="false"/>
  <field name="meta_keywords" type="text_en" indexed="true" stored="false"/>


  <!-- Publish Date -->
  <field name="publish_date" type="pdate" indexed="true" stored="true"/>


  <!-- ========================= -->
  <!-- Copy Fields -->
  <!-- ========================= -->


  <!-- Build unified searchable field -->
  <copyField source="product_name" dest="text"/>
  <copyField source="short_description" dest="text"/>
  <copyField source="long_description" dest="text"/>
  <copyField source="features" dest="text"/>
  <copyField source="meta_keywords" dest="text"/>


</schema>

Below is a sample solrconfig.xml tuned for relevance for an appliance e-commerce setup (AEM Sites + Adobe Commerce + Apache Solr), optimized for multi-category products like those from IFB Appliances.
This configuration focuses on:

<config>


  <!-- ============================= -->
  <!-- Request Handler for Main Search -->
  <!-- ============================= -->
  <requestHandler name="/select" class="solr.SearchHandler">
    <lst name="defaults">


      <!-- Use Extended DisMax -->
      <str name="defType">edismax</str>


      <!-- Query Fields with Boosts -->
      <str name="qf">
        product_name^12
        category^8
        sub_category^6
        features^4
        short_description^3
        text^2
      </str>


      <!-- Phrase Boosting -->
      <str name="pf">
        product_name^20
        category^10
      </str>


      <!-- Minimum match -->
      <str name="mm">2&lt;-1 5&lt;-2</str>


      <!-- Boost functions -->
      <str name="bf">
        recip(ms(NOW,publish_date),3.16e-11,1,1)^2
        rating^1.5
      </str>


      <!-- Boost Queries -->
      <str name="bq">
        in_stock:true^8
        is_best_seller:true^5
        is_new_launch:true^3
      </str>


      <!-- Tie breaker -->
      <str name="tie">0.1</str>


      <!-- Default rows -->
      <int name="rows">20</int>


      <!-- Enable debugging when needed -->
      <str name="debugQuery">false</str>


    </lst>

  <!-- ============================= -->

      <str name="name">productSuggester</str>

      <str name="suggestAnalyzerFieldType">text_en</str>
      <str name="buildOnStartup">true</str>
      <str name="buildOnCommit">true</str>
    </lst>
  </searchComponent>


  <requestHandler name="/suggest" class="solr.SearchHandler">
    <lst name="defaults">
      <str name="suggest">true</str>
      <str name="suggest.dictionary">productSuggester</str>
      <str name="suggest.count">10</str>
    </lst>
    <arr name="components">
      <str>suggest</str>
    </arr>
  </requestHandler>

  <!-- Spellcheck Configuration -->
  <!-- ============================= -->

    <lst name="spellchecker">
      <str name="name">default</str>
      <str name="field">text</str>

      <float name="accuracy">0.7</float>
      <int name="maxEdits">2</int>

When I said “Intent Tagging logic should be implemented in AEM before querying Solr”, I meant:
👉 Solr is a ranking engine.
👉 Intent detection is an experience-layer responsibility.
👉 AEM should interpret what the user wants before building the Solr query.
Below is a clear, production-ready approach for implementing Intent Tagging in AEM (Cloud Service) for an appliance ecommerce setup like IFB.
________________


🎯 Step 1: Define Intent Taxonomy (Business Exercise First)
For an appliance brand like IFB, typical intents are:
Intent
	Example Queries
	buy
	8kg washing machine, inverter ac price
	repair
	washing machine not draining
	service
	IFB service center near me
	manual
	microwave user manual
	accessories
	dishwasher tablets
	compare
	compare 8kg and 9kg
	warranty
	warranty registration
	You must freeze this taxonomy before implementation.

In your schema.xml:
<field name="intent_tags" type="string" indexed="true" stored="true" multiValued="true"/>
During indexing (from Adobe Commerce or AEM):

🎯 Step 3: Build Intent Detection in AEM (Critical Layer)
This should NOT be done in Solr.
In AEM (Sling Model / OSGi Service):
1️⃣ Maintain Intent Dictionary (Configurable)
Create an OSGi configuration:
{
  "buy": ["price", "cost", "buy", "purchase", "under"],
  "repair": ["not working", "problem", "issue", "leak", "noise"],
  "service": ["service center", "technician", "installation"],
  "manual": ["manual", "pdf", "user guide"],
  "accessories": ["tablet", "additive", "spare", "filter"]
}
This must be business-editable (via AEM config or Content Fragment).

2️⃣ Detect Intent Before Calling Solr
Pseudo logic in AEM:
public String detectIntent(String query) {


   if(query contains any service keywords)
       return "service";


   if(query contains numeric price pattern)
       return "buy";


   if(query contains problem keywords)
       return "repair";


   return "buy"; // default
}
You can also use:
* Regex for price (under 40000)
* Regex for capacity (8kg, 1.5 ton)

If intent = repair
q=washing machine not draining

If intent = accessories

* ✅ Best practice is custom indexing pipeline, not a plug-and-play extension
So you should not rely on marketplace extensions for enterprise search.

You have 3 viable options:

OPTION A (Recommended for Enterprise):
Event-Driven Indexing via Adobe Commerce Events
